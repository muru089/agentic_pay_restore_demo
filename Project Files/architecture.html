Multi-agent Google ADK · 3-tier orchestration · gemini-2.5-flash · Safety pre-flight · RAG knowledge base · Diagnostic Supervisor

1 · Full Agent Architecture

3-tier structure: Uber (root_agent) owns auth, safety, routing, and restore sequencing. For suspended account flows, root_agent tracks progress in a persistent session layer — each completed step is recorded so the agent resumes accurately across conversation turns without re-reading the conversation history. Supervisor (SA1_DiagnosticSupervisor) handles ambiguous multi-dimensional health complaints by fanning out DA1, DA5_StorageAgent, and DA6_IntegrationAgent in parallel, then synthesising urgency to surface the highest-impact finding. Single-intent diagnostic queries (storage only / integration only) bypass SA1 and route directly from root. Domain / Squad agents own tool execution and enforce their own prerequisite gates. DA4 is shared — called by root_agent for both active-account plan changes and post-restore upgrades. DA1 is also shared — called by root_agent (fresh start) and by SA1 (diagnostic fan-out). DA2 now handles two distinct billing paths: (1) the suspended-account restore path (balance preview → payment + fee waiver check) and (2) the active-account billing path (monthly invoice payment, no fee waiver, no restore — DA2 sends its own T8 receipt).

2 · Demo Environment

All compute runs on local infrastructure — no cloud servers to provision or deploy. The only external dependencies are two API keys: Google AI Studio (Gemini models + embeddings) and Microsoft Azure Cognitive Services (Content Safety). SQLite and ChromaDB are embedded libraries with no server process.

3 · RAG Knowledge Base

Two separate pipelines: an offline indexing job (rag_seed.py) and an online retrieval tool (T10_SearchKnowledge). The indexing job is re-run whenever the HTML help center pages are updated — in production this would be a nightly scheduled job. T10 is called by root_agent for any general policy or FAQ question that doesn't require account lookup.

4 · root_agent — Restore Sequencing (Persistent State Dispatch)

root_agent manages the full restore flow across multiple conversation turns using a persistent session layer. At the start of each turn, it reads the current checkpoint state and uses a priority-ordered dispatch approach to determine exactly what to do next — only one action fires per turn, and progress is recorded before the turn ends. This makes the multi-step flow reliable and deterministic: the agent always knows where the conversation left off, without re-reading the conversation history.

5 · SA1_DiagnosticSupervisor — Parallel Fan-out & Synthesis

Invoked by root_agent when a customer's complaint is ambiguous — symptoms that could be caused by storage, an integration failure, or an account issue. SA1 fans out all three domain agents in parallel in a single LLM turn, collects their results, and synthesises a ranked finding. Single-intent queries bypass SA1 entirely and route directly to the relevant domain agent. Two demo accounts: 20012 Taylor (Team plan, 95/100 GB — storage is the culprit) and 20013 Blake (Business plan, GitHub auth_failure — integration is the culprit).

This diagram shows what the architecture would look like at scale. The SA-Diagnostics Supervisor is today's SA1_DiagnosticSupervisor; the other three are future state. root_agent continues to own auth, routing, restore sequencing, and safety pre-flight — that doesn't change.
